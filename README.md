# Stand — 30 Days of Spiritual Combat

A mobile-first, audio-ready devotional app built with plain HTML, CSS, and JavaScript. It includes all 30 days, guided device narration, progress tracking, favorites, private reflection notes, dark mode, and responsive design.

## Features

- **SOS mode — "Steady me now"** — a 90-second guided rescue for fearful moments: slow breathing, an anchoring verse, a short prayer, and a declaration. Always one tap away (including a home-screen shortcut), fully offline, with crisis-support resources always visible.
- **Fear-specific tracks** — alongside the 30-day core journey, focused 5-day tracks (Fear of the Unknown, Night Fear & Sleep) with their own progress, notes, and favorites; switch journeys from the ☰ library.
- **Courage stories** — seventeen four-day modules, each built on a single heroic account, covering overwhelming problems, accusation, panic, speaking up, opposition, fear for your children, health fears, financial fear, stepping into the unknown, inadequacy, an unchosen crisis, and starting over. Each walks the same four beats — the fear, the choice, the outcome, what you carry forward — and ends every day with one concrete exercise. Scripture in these tracks is condensed from the public-domain World English Bible — clauses dropped to fit a card, and in places wording from outside the WEB. They are not quotations, and `npm run verify:scripture` reports them separately from the excerpts that are.
- **"Where are you right now?"** — the ☰ library opens with a plain-language list of situations ("I have a court date", "I'm afraid for my child", "I don't know how I'm going to pay for it") that jumps straight into the journey that meets it, so nobody has to browse twenty titles while afraid. The mapping lives in `fearIndex` in `content.js`.
- **Grouped journey picker** — the ☰ library groups journeys under the heading in each track's `group` field (the 30-day journey, fear tracks, courage stories), so the list stays scannable as tracks are added.
- **Prayer composer** (✛) — composes a whole prayer from a reviewed corpus: pick a language, a kind (prayer, forgiveness, grace) and an intention, add an optional personal intention, and reseed for another. Composition is deterministic and offline — nothing is generated at runtime, so every line a reader can see is reviewable in `prayers.js`. Also lists the traditional prayers, with device narration that pauses where each prayer's pacing metadata says to.
- **English and Spanish, interface included** — the app's own chrome is translated, not just its content: 174 interface strings live in `ui.js` as a parallel `{ en, es }` table, and `applyUi()` repaints the shell from `data-i18n` annotations in the markup rather than a hand-maintained list of element ids. That covers buttons, form labels, aria labels, select options, the calm ledger, the journal, the exported `.txt` header, the `.ics` reminder's summary and alarm, and the SOS flow — whose four sets come from `esSos` in `content.es.js`, so the Spanish verses are Reina-Valera rather than a translation of the English ones. `npm run verify:ui` gates it: the two languages must carry the same keys with the same `{placeholders}`, every `data-i18n` attribute must name a real key, the inline English in the markup must match the table character for character, and no key may go unused. It runs in CI.
- **Every prayer and every label on the prayer surface carries both languages**, and so do all 108 devotional days: title, reference, verse, reflection, prayer, declaration and practice, plus week labels, track names and library headings. The choice is app-wide and saved. The same seed composes the same prayer in either language, so switching translates the prayer rather than replacing it.
- **Spanish content lives in `content.es.js`** — a parallel structure with the same day indices, so switching language swaps the words without touching progress, favourites or notes: those are keyed by track and day number, not by text. Spanish scripture is the **Reina-Valera 1909**, public domain; the 1960 revision is not, which is why the edition is pinned and checked. `npm run verify:scripture` asserts all 108 Spanish verses are contiguous substrings of `scripts/es-source.json` and fails the build otherwise — injecting RVR1960 wording is rejected.
- **Side by side** — tick “Show both languages” and each line appears with its translation beneath it, the way a bilingual prayer book sets them. It is one prayer shown twice, not two prayers: the same seed picks the same blocks in both columns, and `npm run validate` checks that each column matches what that language composes on its own.
- **Roman Catholic prayers named as such** — the traditional prayers are grouped and labelled: those shared across the wider Christian tradition, and those that are specifically Roman Catholic devotions. The Marian and Franciscan closings are labelled the same way in the composer, and "As composed" only draws on the traditions in `meta.defaultClosingTraditions`, so a Roman Catholic closing is always a deliberate choice.
- **Fear check-ins and a calm ledger** — optional 1–5 check-ins before and after SOS and on any day; the journal shows your own evidence, like the average fear drop after prayer.
- **Guided narration** with play/pause, adjustable speed, and an automatically selected English voice.
- **Picks up where you left off** — opening the app jumps to your first incomplete day.
- **Library filters** — browse all days, favorites, or completed days from the ☰ menu.
- **Keyboard navigation** — use ← and → to move between days.
- **Installable and offline-ready** — a web app manifest and service worker let you add it to your home screen and use it without a connection.
- **Reflections journal** — open ✎ to read every note in one place and download them as a text file.
- **Daily streak** — completing days on consecutive calendar days builds a streak shown in the progress bar.
- **Verse cards** — the ↗ button shares the day's verse as a designed image via the device share sheet (desktop saves the card and copies the text).
- **Repeat & sleep timer** — loop the guided prayer and let a 5–30 minute timer stop it, for night-time listening.
- **Dark mode on the static pages** — the landing page at `/`, `/fears` and all 108 day pages follow the device's colour scheme. They carry no JavaScript, so the `.dark` class the app toggles never reached them and they rendered full-brightness for a reader whose device was set to dark. They opt in with `class="theme-auto"` plus a `prefers-color-scheme` rule; the app deliberately does not carry that class, because choosing "light" in the app is the *absence* of `.dark` and a bare `:root` rule would override it. The smoke suite checks both token blocks are identical and that an explicit in-app light choice still wins on a dark device.
- **The actual screens** — the landing page shows three captures of the running app (SOS mid-breath, a day with its narration card, a composed prayer), in light and dark variants via `<picture>` so only the matching set is downloaded, each as a WebP (quality 0.9, encoded by Chromium itself) ahead of its PNG fallback: 131 KB for the three instead of 348 KB. `node scripts/build-screenshots.js` regenerates both formats from the real app, so they cannot drift into promising something it does not do, and a unit test checks every screenshot exists as PNG and WebP at the size the page declares.
- **Accessibility audit in CI** — `npm run test:a11y` (`tests/a11y.js`) runs axe-core against every page shape (landing, fear index, day and track pages, policies, the 404) and every app screen and dialog (welcome, day, Steady me now, composer, journal, share, library, and the app in Spanish), at phone width in light and dark: 36 screens against WCAG 2.0–2.2 A/AA and axe's best practices. Any violation fails CI and is printed with its screen and elements. Its first run found a 3.9:1 subtitle on the selected journey chip that no hand-written check covered.
- **Install sheet and home-screen icon** — `manifest.webmanifest` lists maskable icons (`icon-maskable-192.png`, `icon-maskable-512.png`: full-bleed, the cross inside the safe zone, so Android crops the icon to its own shape instead of shrinking it onto a white plate) and four screenshots that Chrome and Edge show when offering to install (`shots/install-*.png`: three phone screens and one desktop window). `node scripts/build-icons.js` and `node scripts/build-screenshots.js --install` regenerate them; `tests/manifest.test.js` checks every listed image exists at its stated size and that the install identity (`id`, `/app`) never moves. Playwright is pinned to an exact version so CI and a laptop render with the same browser.
- **Structured data** — the landing page carries a `WebSite` + `SoftwareApplication` JSON-LD graph. `script-src 'self'` does not block it (ld+json is data, not executable script — verified against the production CSP), and it claims nothing the app has not earned: no ratings, no reviews.
- **Routing** — `/` is the landing page and `/app` is the app. The root used to be the app itself, so the domain opened a hash-routed SPA (landing on `/#1`) rather than the page that explains it. `/about` redirects permanently to `/`, the manifest's `start_url` and SOS shortcut point at `/app` so an installed copy still opens the app, and the service worker's cached shell is `/app` — pointing it at `/` would hand the app shell to everyone opening the site. Saved notes, progress and streaks are unaffected: `localStorage` is scoped to the domain, not the path.
- **Spanish landing page** — `/es` mirrors the root page in Spanish, with its own fear index at `/es/fears`, its own screenshots captured from the app running in Spanish, and a language link in the nav and footer of both. Its screenshots are captured from the app running in Spanish, interface and all.
- **Landing page at the root** — `/` describes what the app does, in the app's own type, palette, and components (it links `styles.css` and reuses `.app-shell`, `.topbar`, `.eyebrow`, and the rest, exactly as the generated day pages do). A call to action sits in the hero, in the nav's mobile menu, and in the footer. The menu is a `<details>` disclosure, so the static pages carry no script beyond the deferred `share.js` enhancement and the open state is announced natively. No pricing.
- **Fear index** — `/fears` is the finder's list as a crawlable page: every situation, grouped by kind of journey, each linking to that journey's first day. Generated from the same `fearIndex` the app uses, so the page and the dialog cannot drift, and CI fails if the committed page falls out of sync.
- **Share row on every day page** — under the practice: Copy link, the device's share sheet where one exists, and X, Facebook, WhatsApp and email. The four platform links are plain intent URLs baked in by the generator from `scripts/share-links.js` (no platform scripts, no tracking parameters), so they work with JavaScript off; `share.js`, the one script a day page loads (same origin, deferred, an enhancement only), reveals the two buttons, copies the canonical page URL and says "Link copied", and falls back to showing the link selected when the clipboard is refused. The caption is the verse and its reference, the same text the app shares. The app's own share button shares the same canonical page (via `dayPagePath`, the function the calendar reminders use) rather than `/app#N`, which only ever previews as the app: a phone that can share files gets the day's share card with the link in its text, one that can share links gets the link, and a desktop gets a dialog with Copy link, Save the day's card and the same four platform links. The app asks for the card at `/cards/{lang}/{track}/{slug}.latest.post.png`, which redirects to the current card (the app knows the day, not the hash); offline or on failure it draws its own verse card instead, and the service worker leaves `/cards/` to the network and the HTTP cache. Under the share row each day page also shows its card ("Share as an image"): the image, a Download link that needs no script, and Share image, which `share.js` reveals only where the device can share files and which fetches the PNG on tap. The link builders and icons live in `share.js`, a browser global and a CommonJS module like `logic.js`, so the pages, the app and the tests use one copy. Every page also states the social card's size and alt text, carries `twitter:*` explicitly and names its `og:locale:alternate`, so a pasted link previews the same everywhere; the card itself is cached at the CDN for a day.
- **SEO day pages, in both languages** — `npm run build:seo` regenerates 216 static, crawlable pages: English under `day/` and `track/<id>/`, Spanish under `es/day/` and `es/track/<id>/`, from `content.js` and `content.es.js`. Spanish slugs are the Spanish titles with accents folded to ASCII (`/es/day/01-firmeza`). Every page carries reciprocal `hreflang` alternates with `x-default` on the English side, so a search engine serves the right language instead of treating the pair as duplicates — the suite fails if the pairing stops being reciprocal. Plus `sitemap.xml` (220 URLs) and `robots.txt`. Every page carries a canonical link, an `og:url`, and the shared social card. `SITE_URL` defaults to production and can be overridden for a staging build. `?track=<id>` links deep-link into a journey. Every day page carries structured data: a schema.org `Article` with its headline, description, scripture citation, position in a `CreativeWorkSeries` named for the journey, and a link to its translation (`workTranslation` on the English side, `translationOfWork` on the Spanish), plus a three-step `BreadcrumbList`. JSON-LD is data rather than a script, so it survives the production `script-src 'self'`; the suite parses all 216 pages from disk and two through the browser under that policy.
- **Privacy, terms and a branded 404** — `/privacy` and `/terms` (and `/es/privacy`, `/es/terms`) are plain-language drafts, pending attorney review, generated by `npm run build:seo` with the same head, nav, footer and hreflang pairing as the other static pages; every static page's footer links to both, and the one contact address is `CONTACT_EMAIL` in `scripts/build-day-pages.js`. `404.html`, generated alongside them, is what Vercel serves for any unknown path: English and Spanish on one page, links to the app, "Steady me now" and both home pages, `noindex`, no script, not in the sitemap.
- **Every static page is a way in, not a dead end** — the day and track pages carry the same nav and footer as the landing page, generated from one `NAV_LINKS` list, so someone who arrives at day 14 of a courage story from a search result can reach SOS, the fear index, or the app itself. A page never links to itself in its own menu.
- **One social card** — `og-card.png` is the shared `og:image` for the landing pages, the fear indexes and the policies (each day page previews with its own card, below), so a shared link previews as the brand rather than a blank grey box. Regenerate it with `node scripts/build-og-card.js`; the PNG is committed because social scrapers fetch it directly and never run JavaScript.
- **A share card for every day** — `api/card.js` renders each day's card on request, in English and Spanish, as `/cards/{lang}/{track}/{slug}.{hash}.{post|og}.png`: `post` is 1080x1350 with the verse, reflection and prayer for posting as an image, `og` is 1200x630 for link previews. `cards.js` decides what a card says and where it lives, for the page generator, the function and the tests alike; the hash covers everything the card shows, so an edit is a new address, the image is cached for a year, and an old address redirects to the current one. Only published day content is drawn, looked up by address; nothing from a request is rendered as text. Rendering is satori (layout to SVG) and resvg (WebAssembly, SVG to PNG) with bundled OFL fonts (`fonts/`, Source Serif 4 and Source Sans 3). `tests/cards.test.js` checks every card's address, both sizes, the redirect and the 404s, and fails if a day's text outgrows the layout it was checked against. Every day page's `og:image`, `twitter:image` and structured-data `image` point at that day's `og` card, with alt text naming the day. After each production deploy the Deploy check workflow runs `npm run verify:cards`, which fetches all 432 cards: the first real request the function gets (preview deployments sit behind a login), and it warms the CDN so a social site asking for a preview never waits on a render.
- **Personalized start** — first-time visitors choose where to begin: the 30-day journey or a focused fear track.
- **Daily calendar reminder, one per day** — the library generates a calendar file (.ics) at your chosen time, with no notifications permission and no server. It is one recurring series with a `RECURRENCE-ID` override for every remaining day of your journey (RFC 5545 §3.8.4.4, the same mechanism calendars use to store a modified instance), so each reminder carries that day’s title, week, scripture, practice, declaration, a short tip, and two links: straight into the day in the app (`/app?track=furnace#3`) and to its crawlable page. The schedule starts at the first incomplete day and stops when the journey ends (`COUNT`); a finished journey starts again from Day 1. The series keeps the fixed `UID` the app has always used and an increasing `SEQUENCE`, so exporting again — after falling behind, switching journey or switching language — **updates** the existing series instead of leaving a second one running, and a reader who exported the old single reminder gets it replaced. Times are deliberately *floating* (no `Z`, no `TZID`): the reminder fires at the chosen wall-clock time wherever you are rather than drifting when you travel, and the chosen HH:MM is printed literally so a daylight-saving jump cannot move an override off its occurrence. The file is built in `reminder.js`, pure so `tests/reminder.test.js` can check it in Node: RFC 5545-conformant, TEXT values escaped (the verses are full of commas), content lines folded at 75 octets, every page link checked against the generated pages, every day of every journey in both languages built and parsed. `slugify` moved into `logic.js` so the app and the page generator cannot disagree about a URL. Known client limit: Google Calendar’s file import does not apply `SEQUENCE` updates to an existing UID, so the status text says to delete and re-import if a duplicate appears. The button says what it will add (“Add 24 reminders to my calendar (Day 7–30)”) and a preview under it shows the first reminder exactly as the calendar will — the same `reminderEntry()` feeds the label, the preview and the file, so the three cannot disagree. On a phone that supports sharing files, the file goes to the share sheet, where Calendar is one tap away, instead of into Downloads; other browsers still get the download. The web link lands on the practice itself (`#practice`, an anchor every generated page carries). The file is published as its own calendar (`METHOD:PUBLISH`, `X-WR-CALNAME:Stand`), which is the cleanest way to delete the whole series later. The two health journeys and the financial one repeat their guardrail in the second reminder’s tip: prayer alongside medical care, never instead of it; not a technique for producing money. The smoke suite opens every link in the file and checks the page shows the day and practice the reminder names. Three options, remembered and kept by a backup restore: start with where you are (the default) or with Day 1; weekdays only, which writes a weekly Monday-to-Friday rule and skips weekends in every override date; and an alert at the time, ten minutes before, or thirty. The status line says where the first reminder lands — today, tomorrow, or the day it moved to when a weekend was skipped. A fourth option adds an evening check-in: a second, five-minute series on the same days at its own time, each entry repeating the morning’s practice, asking how it went, and linking to the day with the fear check-in scrolled into view (`/app?checkin=1#7`). It has its own `UID`, so it can be kept or dropped independently of the morning series; turning it off emits the series once more as `STATUS:CANCELLED` with a higher `SEQUENCE`, which Apple and Outlook honour on import, and the status text names what to delete for a client that does not. **Or subscribe:** the same file is served as a feed from `/calendar.ics` (a Vercel function at `api/calendar.js`, reached through a rewrite), so a calendar app can poll it and the reader never re-exports. The app builds the link from the current options — `webcal://` for Apple Calendar and Outlook, an https copy for Google Calendar’s “From URL” — and the URL carries only the journey, the day to start on, the date of that first reminder, the time, the language and the option flags. Completion never leaves the device, so the feed is date-anchored: a reader who falls behind changes nothing in the app but subscribes again, and the app builds the new URL from where they are. The body is a pure function of the query (its `DTSTAMP` is the start date), cached at the CDN for a day, and the service worker never caches it. It is the product’s only server code; `tests/api.test.js` covers validation, the options, purity and the HTTP contract, and the smoke suite routes the same path to the same handler and checks the link the app builds serves the same series the download does.
- **iOS install tip** — Safari visitors get a one-time, dismissible Add-to-Home-Screen hint.
- **Dark mode** follows your device setting until you choose a theme with ◐.
- **Backup and restore** — download all data as a JSON file and restore it on any device; an erase option removes everything.
- **Welcome screen** introduces the journey on first visit.
- **Print-friendly** — printing a day hides the app chrome and keeps the devotional content.
- Notes, favorites, and progress are stored privately on your device (localStorage), and the deployment ships a strict Content Security Policy.

## Tests

A 512-check end-to-end smoke suite (`tests/smoke.js`) drives the app in headless Chromium against a server that enforces the production Content Security Policy. It runs in CI (GitHub Actions) on every push and pull request, alongside syntax checks and a guard that the generated SEO pages, sitemap and robots.txt match `content.js`. It includes a contrast ratchet — a sweep of every element that renders its own text on the app shell and the four static page shapes, in both colour schemes, failing on any WCAG 2.1 shortfall that is not on a recorded known-debt list. That list is now empty: the gold label colour used to fail on the light palette (`--gold` #b88732 is 2.92:1 on the paper), so text now uses a darker `--gold-text` token (#7f5b1a, 5.60:1 on the paper and 4.74:1 on the gold wash) while borders, fills, the favourite glyph and the whole dark palette keep `--gold`. It also asserts the footer call to action directly across all three static pages — that check was added after `.landing-footer a` was found to beat `.complete-button` on specificity and render the button's text at 2.92:1, under the 4.5:1 AA minimum.

```bash
npm install
npx playwright install chromium
npm test
```

## Publish with GitHub and Vercel

1. Create an empty GitHub repository.
2. Upload this folder or push it with Git.
3. In Vercel, select **Add New → Project**, import the repository, and click **Deploy**.
4. Leave Framework Preset as **Other**. No build command or environment variables are required.

The one function, `api/calendar.js`, is picked up automatically from the `api/` directory; `vercel.json` rewrites `/calendar.ics` to it. Nothing else runs on a server.

A merge to main is not live until Vercel has built it and moved the production alias, and that can lag by minutes with nothing in GitHub to say so. `npm run verify:deploy` fetches the app shell, every script it loads and one page of each static shape from the production site and compares them byte for byte with your checkout, polling for up to three minutes; it exits non-zero naming any file that is missing or differs. The **Deploy check** workflow runs the same script on every successful production deployment, against the deployed commit, so a stale alias shows up as a red check on the commit rather than as a reader seeing last week’s build.

## Audio

The player prefers recorded narration and falls back to the browser's built-in Speech Synthesis API (so the fallback voice depends on the listener's device). Both read the same words: `narration.js` builds the script for a day, an SOS set or a traditional prayer in either language, spelling out scripture references ("Ephesians, chapter six, verses ten through thirteen"), writing breath pauses as ellipses and speaking the WEB's small-caps "LORD" as "Lord", so the recording and the fallback never disagree. Recorded playback supports pause/resume, speed, repeat, the sleep timer, and lock-screen controls (Media Session); a recording that fails to load falls back to the device voice, and `/app?tts=1` forces the device voice.

The SOS screen's support panel lists 988, the Crisis Text Line and 911 as one-tap `tel:` and `sms:` links, gives Spanish readers the Spanish routes (988: press 2, or text AYUDA to 988; Crisis Text Line: text AYUDA to 741741, per both services' own pages), and points readers outside the US to findahelpline.com. The SOS recording ("Hear this prayed") is on the lock screen too, named "Steady me now" with its verse reference, and it stops when the SOS screen closes by the × or Escape; device speech names the day on the lock screen without a scrubber. **Keeping the reader's data:** everything lives in this browser's storage, which Safari deletes after about a week without a visit unless the site is on the Home Screen. Once there is something worth keeping the app asks the browser to keep its storage (`navigator.storage.persist()`), and while the data is still at risk (not an installed copy; on iPhone, or where persistence was refused) and there are three days done or a note, it offers a backup under the progress bar, at most once a month, with “Not now” to put it away. The two timestamps are this device's, outside the backup; erasing all data forgets them. **Error reports:** `report.js` loads first and, when the app's own script throws or a promise is rejected, sends at most three short reports per page load to `/api/report` (a Vercel function) with `navigator.sendBeacon`: the error's name, its message with anything in quotes replaced by `…` and cut to 200 characters, the same-origin file path, line and column, and the page path (no query or hash). No notes, verses, progress, IP address or identifier are sent; the function validates the shape again, logs one JSON line (`"event":"client-error"`) to the Vercel runtime logs and answers 204. Errors from extensions and other origins are ignored, and nothing is sent when the browser signals Global Privacy Control. **Offline listening** is opt-in and per device (Library → “Keep a week of audio on this device”): the recordings for today and the next six days of the reader's journey, in their language, and the four “Steady me now” sets, about 8 MB, are fetched into the Cache API and played from `blob:` URLs, so a lost connection plays the recording instead of falling back to the device voice. `offline-audio.js` decides what to keep (unit-tested against the committed library); the window follows the reader's day, journey and language and drops what falls out of it; nothing is fetched when the device asks to save data; turning it off, or erasing all data, deletes the copies. The preference lives under its own key, outside the backup, because a cache belongs to one device. It needs `connect-src` for the audio hosts and `blob:` in `media-src`, both in the CSP. Recordings are rendered with ElevenLabs by `npm run build:audio` (in CI, the Build audio workflow) and served from the `audio` branch of this repository through the `prayers-audio` Vercel project at `stand-audio.vercel.app`, or optionally from a private S3 bucket through CloudFront (`infra/audio-cdn.yaml`). The build reads voices and delivery settings from `audio-voices.json`, files each MP3 under a key that carries the hash of its script and settings (`en/day/core/01-stand.<hash>.mp3`, `es/prayer/our-father.<hash>.mp3`), and writes `audio-manifest.js`, which the app loads to find the recording for the current day, SOS set or traditional prayer in the current language. Everything is narrated by one voice in both languages, the voice REMAM's prayer audio uses, so the two apps sound the same. A traditional prayer is rendered at the pacing its entry in `prayers.js` declares: the same break anchors the device voice turns into silences become `<break>` tags in the script, and its speed, stability and style override the per-kind defaults. `npm run verify:audio` runs in CI and fails when an item in the manifest no longer matches the current script or settings, printing the command that re-renders exactly those items, so a content edit can never ship stale audio; `npm run verify:audio -- --remote` also asks the audio host for every file in the manifest. `--allow-stale` lists stale items without failing on them: the Build audio workflow checks the manifest that way before it renders, since stale items are what a run is for, and after a dry run or a partial run; malformed entries and orphans still stop it, and CI on the manifest's pull request stays strict. The workflow pushes the recordings to the `audio` branch (pruning takes that neither the new manifest nor main's still names, via `scripts/prune-audio.js`, so a re-render does not leave its predecessor behind), waits until the host serves them all, pushes the manifest as a branch named `audio-manifest-<run>` together with a bumped service-worker cache name (`npm run bump:sw`, so installed apps pick the new manifest up on their next visit rather than one visit later), opens the pull request itself and dispatches CI on the branch (a PR opened by the workflow token starts no workflows on its own; the repository setting "Allow GitHub Actions to create and approve pull requests" must be on, else the run says to open it by hand). Days without an entry keep using device narration. The API key is read only from `ELEVENLABS_API_KEY` (the workflow accepts the repository secret as `ELEVENLABS_API` or `ELEVENLABS_API_KEY`); `--dry-run` lists what a build would render and how many characters it would spend, `--max-chars <n>` refuses to start a run that would spend more than that (the workflow's `max_chars` input, 40,000 by default, so an edit that touches every script cannot quietly re-render the whole library), `--only en/day/core --limit 3` renders a first look, and `--upload --bucket <name>` puts the files in S3 (needs `@aws-sdk/client-s3` installed and AWS credentials with `PutObject` on that bucket alone). While a recording plays, the lock screen and notification shade show the day's or prayer's title with the app icon, a progress bar and a scrubber, and offer pause, stop and ten-second skip back and forward; device narration shows play and pause only, since it has no position to report.

## Prayer corpus

`prayers.js` holds the prayer corpus and `compose.js` the composition engine, both ported from the REMAM project (`dougdevitre/remam`). Every block carries English and Spanish. The corpus keeps REMAM's shape: modes, each with intentions and ordered slots, where every block is a complete sentence or two so any one block per slot reads as a whole prayer.

`npm run validate` checks the corpus the way REMAM validates its own, in every language it declares — every mode composes at both lengths with no missing translation, closings carry a style and a tradition, the UI strings are complete, and the audio pacing stays inside the generator's limits (speed 0.7–1.2, stability and style 0–1, at most 6 breaks per language, each 0–3 seconds, every break anchor an exact substring appearing exactly once in that language's text). It also checks that one seed picks the same blocks in both languages. It runs in CI.

`meta.defaultClosingTraditions` decides which closings "As composed" draws on; it ships as `["universal"]`. Every traditional prayer is listed either way, under its own labelled heading.

**Kept in step with REMAM.** The traditional prayers are REMAM's, word for word, and stay that way on purpose: one text for both apps, recorded in the same voice. `scripts/remam-lock.json` names the REMAM commit they were last synced from and holds a hash of each prayer's name, text in each language and audio pacing there (hashes, not a second copy of the text). `npm run verify:remam` runs in CI with no network and fails when a prayer in `prayers.js` differs from the lock without a recorded reason, naming the prayer and the field. Changing a traditional prayer therefore goes:

1. Make the change in REMAM (`packages/data/content/prayers.json`) and merge it there.
2. `npm run sync:remam -- ../remam` shows what changed since the lock; add `--write` to copy it into `prayers.js` and move the lock to that commit. It refuses to overwrite a field Stand overrides, lists prayers REMAM added (each needs a `tradition` tag before it is imported) or removed (never deleted here), and says when REMAM's composer corpus changed.
3. `npm run verify:audio` then names the recordings to re-render, and the Build audio workflow renders exactly those.

When a prayer should read differently here and not upstream, `node scripts/remam-sync.js override <id> <field> "<reason>"` records Stand's current value and the reason in the lock; the check fails again if that field changes later, or if REMAM adopts the same text (a sync then drops the override). A prayer that exists only in Stand goes under `standOnly` with a reason. The composer corpus (modes, intentions, slots) and `compose.js` are not compared: they are Stand's fork (no Laudato Si' slot or creation/defenders intentions; fear and courage added; side-by-side languages). Each app renders its own recordings: Stand's are content-addressed and cached for a year on its own host, REMAM's live in its S3 bucket, and a text change costs one re-render per app of only the prayers it touches.

## Pastoral review

Until a pastoral advisor has reviewed it, the app labels its devotional content a draft (`meta.reviewNote` in `prayers.js`). `npm run build:review` writes `.review/stand-review.html`: every day of every journey, the SOS sets, every composer block, the traditional prayers and the fear-finder phrases, with English and Spanish side by side. It is published as a private claude.ai artifact (with the `db` and `user` capabilities), where the reviewer marks each item Approve or Needs change with a note; it is never committed or deployed.

Each item has a stable id (`day.core.01`, `sos.2`, `compose.prayer.body.fear.3`, `trad.memorare`) and a hash of its text. A decision is stored with the hash it was made against, so when text changes the workbook shows that decision as out of date rather than carrying the approval over. Spanish lines that address the reader in the masculine (`estoy confundido`) are marked as questions for the reviewer. A "needs change" note becomes a content PR, and only the audio for the items it touches is re-rendered.

## Content note

All scripture in the app is public domain. The 30-day journey, the two fear tracks and the four English SOS sets quote the **World English Bible**; `npm run verify:scripture` checks every one of those 44 excerpts against `scripts/web-source.json` and fails if any is not drawn from that text. It runs in CI. Two changes are applied to the WEB before comparing and no others are permitted: `Yahweh` → `the LORD`, and Ephesians 6:14's `utility belt` → `belt`.

Those excerpts previously read as NIV, which is not licensed for redistribution. The swap removed the question rather than answering it.

The 68 courage-story excerpts used to be **condensed** from the WEB rather than quoted from it, and were reported separately rather than gated. Each one is now a contiguous substring of the WEB text (case and trailing punctuation aside), chosen to keep the clause the day's reflection leans on, so the same gate covers all 112 English excerpts and the four SOS sets. Where the WEB's wording differs from the paraphrase a reader may remember — “dying” rather than “perishing” in Mark 4:38, “given to the LORD” rather than “lent” in 1 Samuel 1:28 — the WEB wins, because the app calls these scripture excerpts and they should be exactly that.

`scripts/es-source.json` holds the Reina-Valera 1909 text for the same 105 references — the 108 Spanish days and the four Spanish SOS sets, both gated, extracted from `scrollmapper/bible_databases`, which names the edition (`SpaRV: La Santa Biblia Reina-Valera (1909)`) and tracks a licence per translation. A widely-used alternative was rejected: it labelled its Spanish text only "Reina Valera" with no edition or licence, admitted the files were crawled, and listed copyrighted translations for other languages.

`scripts/web-source.json` holds the WEB text for the 105 references the app cites, extracted from the `world-english-bible` npm package (which packages ebible.org's text). It is committed rather than installed: 20 KB of public-domain verse beats an 11 MB dependency whose own `package.json` declares `UNLICENSED`.
